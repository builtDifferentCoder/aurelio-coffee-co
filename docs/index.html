case study / ai engineering

Aurelio Coffee Co. — Support Agent

live & deployed
live demo source contact

Most "AI support bot" demos are one LLM call wearing a knowledge base as a costume. This one routes intent, retrieves grounded context, calls real backend tools, and knows the difference between "I can answer this" and "a person needs to handle this" — then runs on a public URL, not a notebook.

how a message moves through it

user → frontend (Next.js, SSE streaming) → backend (FastAPI /chat/stream) → agent (LangGraph, per-session memory) → router (hardcoded rules, then Haiku classifier) → rag_node (Chroma retrieval, confidence-gated) → tool_node (order/subscription tools, session-scoped auth) → escalation_node (deterministic human handoff) → off_topic_node (deterministic redirect)
Router first, LLM second. Refund and damage-claim requests are caught by keyword/pattern rules before any model call — escalation for financially sensitive cases shouldn't depend on how a prompt happened to classify that day.
RAG only answers from what it retrieved. A confidence threshold on retrieval distance means a weak match returns nothing rather than three loosely-related docs for the model to improvise around — off-topic and injection attempts get filtered before they reach generation.
Escalation and off-topic replies are not model-generated. Fixed, deterministic responses — the one place in the system where you don't want the LLM getting creative.

what it proves

Grounded retrieval

19 knowledge docs, chunked by semantic boundary with category metadata, embedded locally via Chroma's built-in ONNX model — no per-query embedding API cost.

Real tool-calling

Order status, subscription lookups, and pause/resume — with a ~10% simulated failure rate so the agent has to actually handle errors, not just the happy path.

Session memory

Per-thread conversation state via LangGraph's checkpointer — follow-up questions correctly resolve pronouns and prior context across turns.

Adversarial testing

20 scripted attacks — prompt injection, jailbreaks, tool misuse, escalation edge cases — with a documented trail of what broke and what got fixed.

what adversarial testing actually found

found fixed A natural multi-item request ("check these two orders and pause my subscription") crashed the session — the agent only handled one tool call per turn, and Anthropic's API requires a result for every call issued. Now resolves all of them.
found fixed "I want to cancel and get my money back" slipped past the escalation keyword filter and reached the tool node, which began speculating about refund criteria not in the actual policy. Escalation patterns broadened to catch intent, not just exact phrases.
found fixed Without any authentication, one session could read another customer's order details — a refusal that appeared in one test was model improvisation, not an enforced control. Sessions now bind to a self-reported email, and tool responses are scoped to it at the data layer.

stack, cost & honest limits

stack

  • Next.js — Vercel
  • FastAPI — Render
  • LangGraph + Claude Haiku
  • Chroma (local, ONNX embeddings)

what this would cost a client

Roughly $3,000–$6,000 fixed-price for this scope — RAG design, 3-4 custom tool integrations, escalation logic, and deployment. Ongoing tool additions or maintenance as a separate retainer.

known limitations

  • No real user authentication — session identity is self-reported
  • In-memory state resets on redeploy
  • Single-instance deployment only

questions worth asking me about this

Why a router node instead of one prompt with everything?
Escalation on refunds and damage claims is a decision with financial consequences — I didn't want that resting on probabilistic classification alone. Hardcoded rules catch the high-stakes cases first; the LLM only classifies what's left.
What was the hardest bug?
A natural multi-item request would crash the whole session, because I'd only tested single tool calls. It taught me to always test multi-tool-call inputs, not just the happy path — that's now a permanent item in how I test any agent.
What would you change for a real production deployment?
Redis-backed checkpointing for multi-instance state, a stronger embedding model once the corpus justified the cost, and unifying session identity into one passed-through context object instead of a state field plus a separate contextvar.
